# RFC 9000 Section 10.3 — Stateless Reset

## Status: Implemented

## Overview
Stateless Reset allows an endpoint that has lost connection state (e.g., after a restart) to signal the peer that the connection is no longer valid. The mechanism uses a 16-byte token that the peer can recognize without any shared cryptographic state.

## Implementation

### Token Computation (`src/quic/stateless_reset.zig`)
- `computeToken(static_key, conn_id)` — HMAC-SHA256 truncated to 16 bytes
- Deterministic: same key + CID always produces the same token
- Server uses a single `static_reset_key` for all connections

### Packet Generation (`src/quic/stateless_reset.zig`)
- `generatePacket()` — produces a packet that looks like a short header packet
- First byte: long header bit cleared (0x80=0), fixed bit set (0x40=1)
- Random prefix bytes + stateless reset token as last 16 bytes
- Minimum 21 bytes; capped at triggering packet size to avoid amplification

### Detection (`src/quic/stateless_reset.zig`)
- `isStatelessReset()` — checks last 16 bytes against known peer tokens
- Packets < 21 bytes are never stateless resets

### Connection Integration (`src/quic/connection.zig`)
- `static_reset_key: [16]u8` — key for deterministic token generation. A
  server connection takes the `ConnectionManager`'s key (via
  `ConnectionConfig.static_reset_key`), so the tokens it advertises are the
  ones the manager's resets carry; a client's is random per connection
- `LocalCidPool.registerInitialCid()` and `issueNewCid()` accept optional static key
- Server includes `stateless_reset_token` in transport parameters (RFC 9000 §18.2)
- Peer's initial reset token from transport params stored in `peer_cid_pool`
- `matchesStatelessReset(data)` — checks a datagram against the tokens of every
  peer CID not yet retired
- `handleStatelessReset(datagram)` — on a match, enters draining without sending,
  sets `received_stateless_reset` and `local_err.reason = "stateless reset"`; the
  connection terminates after the draining period like any other close

### Server-Side Sending (`src/quic/connection_manager.zig`)
- Server generates `static_reset_key` at startup
- When a short-header (1-RTT) packet arrives for an unknown CID, sends stateless reset
- Reset packet one byte smaller than the trigger (§10.3.3 looping, anti-amplification)
- Never sent for a trigger under 43 bytes (`MIN_RESET_TRIGGER`): anything that
  short may itself be a reset, and a tiny packet buys too small a reply to
  hide its token among random bytes
- Rate-limited server-wide by a token bucket in `ConnectionManager.reply_limits`
  (`Config.stateless_reply_rate`, 200/s by default), since a spoofed source
  can trigger it. Version Negotiation and CONNECTION_REFUSED have buckets of
  their own, so reset-triggering junk cannot starve them

### Detection (§10.3.1)
- Client (`Connection.handleDatagram`) and server (`ConnectionManager.route`):
  when the first packet of a datagram is a short header that fails to decrypt
  (`recv` returns `error.UndecryptablePacket`), the whole datagram's last 16
  bytes are checked with `handleStatelessReset`
- Server, unknown DCID: a reset's DCID is random, so the manager keeps
  `reset_token_map` from every connection's peer tokens (resynced in `syncCids`
  when the peer CID pool's `generation` moves). A short-header datagram for an
  unknown DCID is looked up there before any reset of our own is considered
- Tokens are compared in constant time (`crypto.timing_safe.eql`); the server
  map is keyed by SipHash-128 of the token under a random per-manager key, so
  a lookup's timing reveals nothing about token bytes

## Caveats
- Client MUST NOT include `stateless_reset_token` in transport params (enforced by only setting it for `is_server`)
- The server only sends resets for 1-RTT packets (short header); long header packets for unknown connections are ignored
- Tokens of every non-retired peer CID are checked, including ones not yet used
  (§10.3.1 says only CIDs in use); `in_use` tracking is not reliable enough to
  filter on
- With QUIC-LB steering across workers, a client's reset lands on whichever
  worker the random DCID routes to; only that worker's `reset_token_map` is
  consulted
- A connection in the closing state ignores resets and times out as usual
