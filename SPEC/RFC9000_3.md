# RFC 9000 §3 — Stream States (and what happens after them)

Covers the terminal states of §3.1–3.4 and the question the RFC leaves to the
implementation: when the memory behind a stream can be given back.

Implementation: `src/quic/stream.zig` (`Stream`, `StreamsMap`),
`src/quic/connection.zig` (frame handling), `src/event_loop.zig` (drain point).

## State tracking

The RFC's state machines are not modelled as an enum. Each half carries the
flags the transitions are defined in terms of, and the states are read off them:

| RFC state | How it is recognised |
|---|---|
| Send: Ready → Send | `SendStream.write_offset > 0`, nothing sent yet |
| Send: Data Sent | `fin_sent` |
| Send: Data Recvd | `fin_sent` and `!hasUnackedData()` |
| Send: Reset Sent/Recvd | `reset_err != null` |
| Recv: Recv | stream exists, `fin_offset == null` |
| Recv: Size Known | `fin_received` (`sorter.fin_offset` set) |
| Recv: Data Recvd | `recv.allReceived()` — `sorter.isFullyReceived()`: no hole up to the final size |
| Recv: Data Read | `finished` — `read()` returned null past the FIN |

`Stream.closed_for_gc` marks the composite terminal state of §3.4: our FIN is
on the wire and the receive side has reached Data Recvd — the peer's FIN
*and every byte before it* have arrived. A FIN that overtakes earlier data
leaves a hole; closing then would reclaim the stream before the
retransmission filling the hole arrives, and it would be dropped as a
frame for a closed stream. It is set either when a STREAM frame is handled
(`connection.zig`, the FIN or the one filling the last hole) or by
`StreamsMap.collectClosedStreams()`, whichever notices first, and it is what
makes the stream count against `consumed_bidi_streams` for the MAX_STREAMS
sliding window.

## Reclamation

`closed_for_gc` is **not** enough to free a stream. Our FIN having been sent
says nothing about it having been received: PTO recovers a lost FIN by queueing
everything from `ack_offset` to `send_offset` for retransmission and re-packing
it from the send buffer, which it cannot do once the stream is gone. Removing streams at FIN
time is what broke `handshakeloss` and `transferloss` against neqo, where the
server served its response once and then spent 285 s sending bare ACKs.

`Stream.isDisposable()` is the single predicate, and it adds the two conditions
that make the send side genuinely finished:

    closed_for_gc and retransmit_count == 0 and !send.hasUnackedData()

`hasUnackedData()` has to treat the FIN separately from the bytes. ACK ranges
cover byte offsets and the FIN is not a byte, so `ack_offset` stops at
`write_offset` and can never show the FIN as delivered — the original
`ack_offset < write_offset + 1` test was true forever, which made every stream
that had ever sent a FIN permanently unacknowledged. `SendStream.fin_acked` is
set from the `fin` flag of the acked frame instead. RESET_STREAM ends the send
side the same way: RFC 9000 §3.1 forbids STREAM frames after it, so its unacked
bytes are never coming back.

Three places evaluate it, all through `StreamsMap.disposeIfSettled()`:

1. **ACK processing** — the ACK that retires the last unacked byte is the exact
   moment the stream stops being needed. O(1), and the path that fires for
   almost every stream.
2. **STREAM+FIN handling** — for a stream whose send side was already settled
   when the peer's FIN arrived.
3. **`collectClosedStreams()`** — a sweep that catches whatever the other two
   missed: the 64-entry disposal queue is allowed to fill, and a stream can
   settle without any further ACK arriving to trigger a check. `needs_gc_scan`
   stays set while any stream is still awaiting reclamation.

Disposal is deferred rather than immediate. `disposeIfSettled` only queues the
stream ID; `StreamsMap.drainDisposalQueue()` removes and frees it, and the
event loop calls that once per cycle, *after* the protocol layer has polled.
An H3 or WebTransport `poll()` loop therefore always sees a live stream for the
data that arrived in the same cycle.

## Receive-only streams

A unidirectional receive stream has no send side to wait for an ACK on, so
`ReceiveStream.isDisposable()` is a different predicate: the data is all out
(`finished`, or `sorter.isComplete()`, or the peer reset it) **and** the
consumer has said it will not read again.

That second half is the part that cannot be inferred. `finished` flips inside
`read()`, which is called by the protocol layer itself, so at that instant the
layer has the bytes but has not yet delivered them — and it still holds
per-stream state keyed by the ID: H3's control and QPACK streams, WebTransport's
`stream_bufs` and `fin_delivered`. Reclaiming on `finished` alone would drop a
WebTransport FIN event on the floor and would let a peer close a critical stream
without `checkCriticalStreams` ever seeing it.

So the consumer calls `StreamsMap.releaseRecvStream(id)` at the point it has
handed the FIN to the application — the two FIN-delivery sites in
`WebTransportConnection.pollWtStreamData`, and the plain-QUIC uni loops in
`event_loop.zig`. H3's critical streams are never released and so are never
reclaimed, which is the right answer by construction rather than by special
case. Both `identifyPeerUniStreams` and `identifyWtUniStreams` also release a
stream that finished without ever becoming identifiable, so a peer cannot leak
one `ReceiveStream` per zero-length uni stream it opens.

Release is O(1) and queues onto the same disposal queue bidi streams use.
Because nothing re-offers a released stream, a dropped enqueue would strand it;
`recv_disposal_overflow` makes the next drain re-scan `recv_streams` instead.

## Frames for a stream that is gone

Under loss the peer retransmits data we acknowledged just before reclaiming the
stream. `getOrCreateStream()` would build a fresh `Stream` for it — one nothing
would ever close, whose close would be counted a second time against
MAX_STREAMS. `StreamsMap.next_peer_bidi_to_open` is the watermark that separates
the two cases: an ID below it was opened and reclaimed, and
`error.StreamAlreadyClosed` tells `connection.zig` to drop the frame.
`next_peer_uni_to_open` does the same for `getOrCreateRecvStream`, and a
retransmitted FIN is kept from counting twice by `ReceiveStream.closed_counted`.

The watermark is exact only because §3.2's implicit opening is honoured. A peer
may use stream IDs out of order, and using ID *n* opens every lower ID of the
same type; `getOrCreateStream` materialises those lower streams before returning
the requested one. Without that, an ID below the watermark could still be a
stream we had never been told about, and rejecting it would drop a legitimate
new stream.

The number of streams a peer can make us materialise is bounded by the
MAX_STREAMS credit we granted: `connection.zig` raises STREAM_LIMIT_ERROR for an
ID at or above `max_incoming_bidi_streams` before `getOrCreateStream` is
reached.

Streams we opened need the same distinction. RFC 9000 §19.5, §19.8 and §19.10
make a frame naming a local stream "not yet created" a STREAM_STATE_ERROR, and
one that is missing from the maps may instead have been opened and reclaimed —
our ACK of the peer's FIN lost, say, so it retransmits. `next_bidi_stream_id` /
`next_uni_stream_id` are the watermark, and `StreamsMap.localNeverOpened()` makes
the call for STREAM, STOP_SENDING and MAX_STREAM_DATA. Asking the bidi map
instead closes the connection on every such retransmission, and on every
STOP_SENDING for one of our uni streams, which are never in that map.

## Uni send streams live in their own map

`streams` holds bidi streams only; our uni streams are in `send_streams`. Every
sweep of the send side has to visit both: RESET_STREAM and STREAM_DATA_BLOCKED
(`queueSendSideFrames`), the PTO sweep (`queueStreamPtoRetransmissions`), and
reclamation.

A uni `SendStream` has no receive half to wait on, so `SendStream.isDisposable()`
is its own predicate:

    not pinned, and either
        fin_acked and ack_offset >= write_offset     (§3.1 Data Recvd)
        reset_err set and RESET_STREAM queued

Both halves of the first are needed: the FIN can be acked ahead of bytes that a
lost packet carried. `StreamsMap.disposeUniIfSettled()` puts the stream on the
shared disposal queue from two places — the ACK path, as for bidi streams, and
`queueFlowControlUpdates` straight after the RESET_STREAM goes into the pending
queue. The drain frees it and counts it closed. As with receive streams, nothing
offers a settled stream a second time, so `send_disposal_overflow` makes the next
drain re-scan `send_streams` when the queue was full. WebTransport and H3 needed
nothing new: their drains already drop whatever they key by a disposed ID,
`wt_uni_streams` and `reset_delivered` included.

**A reset stream goes when its RESET_STREAM is queued, not when it is acked.**
§3.1 keeps the stream until "Reset Recvd", and quic-go does, because its
retransmission is driven from the stream. Here the frame carries everything a
resend needs — stream, code, final size — and the packet that carried it
records all three (see "Control frames" below), so a lost RESET_STREAM is
rebuilt from that record and the stream is not needed for it. It is marked
queued only once `PendingFrameQueue` accepted it; a full queue leaves it for
the next pass.

**The ordering is what lets WebTransport report a peer's STOP_SENDING.** The
frame resets the stream when it arrives, but the stream only becomes disposable
once the send pass has queued its RESET_STREAM, and the drain that frees it runs
after the next protocol poll. So `pollWtStreamAborts` always sees it.

**H3's critical streams are pinned.** H3 writes to its control and QPACK
streams through `*SendStream` pointers it keeps for the whole connection. None
is ever FIN'd, but a peer's STOP_SENDING resets one, and reclaiming it would
leave H3 writing to freed memory. `SendStream.pinned` exempts them; RFC 9114
§6.2.1 forbids closing them anyway.

Measured on the Chrome firehose (40 s of `/firehose?size=16384`, a FIN'd 16 KiB
uni stream every 8 ms, ~5,000 streams): server RSS went 4 → 178 MiB, linearly,
while nothing was reclaimed; it now levels off at 6 MiB within four seconds.

## The allocator matters

Reclaiming a stream returns its buffers to whatever allocator the application
gave the connection. Every server in `apps/` used to pass an `ArenaAllocator`,
where `free` is a no-op — the stream was gone from the map but its memory was
not reusable, and the process still grew linearly. They pass
`std.heap.smp_allocator` now. Clients keep the arena, because they exit.

## Send buffers

`SendStream.write_buffer` is indexed relative to `buf_base`, the stream offset
of its first byte, not by absolute offset — `bufferedAt()` is the only way in.
`onAck` drops the acknowledged prefix, so a stream holds roughly what is in
flight rather than everything it has ever sent.

Two conditions gate the memmove, and both matter. A flat 64 KiB threshold on
its own is quadratic against an application that writes ahead: an 8 MB write
acknowledged in 64 KiB steps copies ~512 MB and costs two thirds of bulk
throughput (20.0 → 7.2 MB/s on `tools/bench_local.sh`). Requiring the discarded
prefix to be at least as large as the remainder makes the copying amortised
O(1) per byte, and the benchmark is back to unchanged.

Capacity is handed back too. Once the unacknowledged bytes fall under a
quarter of the buffer's capacity, and that capacity is past
`RETAINED_CAPACITY` (64 KiB), `onAck` moves them into an allocation twice
their size, never below the floor. A 6.25 MiB burst otherwise kept its
8.6 MiB buffer until the stream closed; now it drops back to 64 KiB. The
factor of two either side keeps grow/shrink amortised, and `writeData`
reuses the acknowledged prefix before growing, so streaming that fits the
current capacity never reallocates. The receive side keeps no bytes once
read; `FrameSorter` releases its chunk array when it drains past 64 slots, as a
reordering burst can leave it sized for a thousand holes.

`ack_offset` is the safe watermark because it is where PTO retransmission
starts (`queueStreamPtoRetransmissions`). Loss detection can still name a range
below it — a lost packet whose bytes a later ACK covered — so `queueRetransmit`
trims to `ack_offset` rather than reaching for bytes that are gone.

## Send credit and backpressure

A write is never refused for want of the peer's credit. `writeData` buffers
whatever it is given: HTTP/3 frames, capsules and the WebTransport stream header
all go through it whole, and a partial write would split them. So an application
needs another way to learn it is ahead of the peer, or a peer that stops
granting MAX_DATA lets it queue memory without bound. Safari is such a peer
(WebKit bug 319818).

`Connection.sendCapacity()` is the peer's MAX_DATA less every stream byte
already written, sent or not; `streamSendCapacity(id)` narrows it by the
stream's MAX_STREAM_DATA. Counting at write time, as quiche and quinn do, is
what makes a backlog the packer has not reached yet count. The packer still
charges connection flow control as it sends, and is unchanged.

The written total is `SendLedger.committed`. `writeData` is called on a
`SendStream` directly from some thirty places that never see the map, so each
stream points at a ledger the map allocates with its first stream — on the heap,
because the client's `connect()` returns the connection by value.

A reset gives back what it never sent. RESET_STREAM names `send_offset`, the
highest offset that went out, as the final size: buffered bytes were never sent,
may lie past the peer's window, and a final size beyond the window is a
flow-control violation to the peer (§4.5). The ledger drops the same difference,
and `writeData` discards anything written after the reset.

There is no congestion-window term — quiche's is recomputed only per received
packet and goes stale in between — and no local buffer budget of the kind
quinn's `send_window` imposes, so a peer granting a large window over a slow
path still lets an application queue that much. A budget would be one more term
in the minimum.

WebTransport builds on these: `WebTransportConnection.sendCapacity(session_id)`,
`streamSendCapacity`, and `notifyWritable`, which the WT poll re-checks every
cycle so MAX_DATA, MAX_STREAM_DATA, WT_MAX_DATA and a reset's refund all wake a
waiter without a hook in each frame handler.

## Receive credit

Each `ReceiveStream` carries `receive_window`, the highest offset we have
allowed the peer, and `handleStreamFrame` / `handleResetStream` refuse
anything past it with `error.FlowControlError` → FLOW_CONTROL_ERROR (§4.1,
§4.5). Windows start from `ConnectionConfig.initial_max_stream_data_*` (what
the transport parameters advertise) and `queueFlowControlUpdates` re-grants
`receive_window_size` beyond `bytes_read` once a quarter of it is consumed —
for bidi streams and for the peer's uni streams alike, which H3 control/QPACK,
WebTransport and MoQ uni streams depend on past their first megabyte.

Credit is returned as data is *read*, so a consumer that stops reading holds
the peer at one window. A consumer that reads bytes into a buffer of its own
counts them in `ReceiveStream.retained` until it lets go of them, so credit
tracks what the application took rather than what was moved up a layer. The H3 layer relies on that for
`H3Connection.pauseBody`: a paused request body stays unread in QUIC.
`WebTransportConnection.pauseStream` does the same for a WebTransport stream,
except that the read which identified the stream (its type prefix and
whatever arrived with it) has already been taken, so the peer can be up to
that much past one window.

**Connection-level receive accounting** (§4.1, §4.5). Each receive stream
charges the connection window with the growth of its highest offset — or its
final size on RESET_STREAM — so the window bounds the sum over streams, and a
retransmission or a repeated RESET_STREAM charges nothing
(`Connection.chargeConnWindow`; FLOW_CONTROL_ERROR past it). Credit comes back
only as the consumer reads (`ReceiveStream.read`), or when a reset or a freed
stream abandons what it held; `queueFlowControlUpdates` harvests it via
`StreamsMap.takeConnCredit` before deciding on MAX_DATA. A consumer that stops
reading therefore holds the whole connection, not just its stream, at one
window.

## Control frames

RFC 9000 §13.3 lists what must be resent when the packet carrying it is lost.
`PacketPacker` records each such frame in the `SentPacket`
(`SentControlFrame`, at most `MAX_CONTROL_FRAMES_PER_PACKET` = 4 per packet;
further ones wait for the next packet, as do frames that do not fit), and
`Connection.requeueLostControlFrames` turns a lost record back into a frame:

| Recorded | Resent as |
|---|---|
| MAX_DATA, MAX_STREAMS | the current limit, not the lost one |
| MAX_STREAM_DATA | the stream's current window, unless its final size is known |
| DATA_BLOCKED, STREAM_DATA_BLOCKED, STREAMS_BLOCKED | only while still blocked at that limit |
| RESET_STREAM | verbatim from the record (the uni stream may be gone) |
| STOP_SENDING | until the stream reaches Data Recvd or Reset Recvd |
| NEW_CONNECTION_ID | from the CID pool while that sequence number is live |
| RETIRE_CONNECTION_ID | verbatim, until an ACK for that sequence number arrives |
| NEW_TOKEN | a freshly minted token |

PING, PATH_CHALLENGE/RESPONSE, ACK_FREQUENCY and IMMEDIATE_ACK are not resent.

`PendingFrameQueue` is fixed at 128 entries. `push` drops a frame that does
not fit and is kept for frames that are safe to lose; `tryPush` reports
failure, and producers of frames the peer must see retry: RESET_STREAM and
STOP_SENDING are marked queued only on success, credit generators run only
when their frame is sure to fit (they commit the new limit as they return it),
and lost-frame resends and CID/token issuance fall back to
`Connection.control_retry`, drained ahead of the next send. One slot is held
back so CONNECTION_CLOSE always gets in.

RETIRE_CONNECTION_ID is sent only for peer CIDs we actually hold (and for a
late CID already below Retire Prior To), never for every number the jump
spans, so a Retire Prior To of 2^62−1 costs one frame. Retirements awaiting
an ACK (`Connection.retiring_cids`) are capped at twice our
`active_connection_id_limit`; past that the peer gets CONNECTION_ID_LIMIT_ERROR
(RFC 9000 §5.1.2), as quic-go and quinn do. That cap is what keeps
`control_retry` bounded.
