# RFC 9000 §3 — Stream States (and what happens after them)

Covers the terminal states of §3.1–3.4 and the question the RFC leaves to the
implementation: when the memory behind a stream can be given back.

Implementation: `src/quic/stream.zig` (`Stream`, `StreamsMap`),
`src/quic/connection.zig` (frame handling), `src/event_loop.zig` (drain point).

## State tracking

The RFC's state machines are not modelled as an enum. Each half carries the
flags the transitions are defined in terms of, and the states are read off them:

| RFC state | How it is recognised |
|---|---|
| Send: Ready → Send | `SendStream.write_offset > 0`, nothing sent yet |
| Send: Data Sent | `fin_sent` |
| Send: Data Recvd | `fin_sent` and `!hasUnackedData()` |
| Send: Reset Sent/Recvd | `reset_err != null` |
| Recv: Recv | stream exists, `fin_offset == null` |
| Recv: Size Known | `fin_received` (`sorter.fin_offset` set) |
| Recv: Data Recvd | `sorter.isComplete()` |
| Recv: Data Read | `finished` — `read()` returned null past the FIN |

`Stream.closed_for_gc` marks the composite terminal state of §3.4: our FIN is
on the wire and the peer's FIN has arrived. It is set either when the FIN
frame is handled (`connection.zig`) or by `StreamsMap.collectClosedStreams()`,
whichever notices first, and it is what makes the stream count against
`consumed_bidi_streams` for the MAX_STREAMS sliding window.

## Reclamation

`closed_for_gc` is **not** enough to free a stream. Our FIN having been sent
says nothing about it having been received: PTO recovers a lost FIN by
resetting `send_offset` back to `ack_offset` and re-packing from the send
buffer, which it cannot do once the stream is gone. Removing streams at FIN
time is what broke `handshakeloss` and `transferloss` against neqo, where the
server served its response once and then spent 285 s sending bare ACKs.

`Stream.isDisposable()` is the single predicate, and it adds the two conditions
that make the send side genuinely finished:

    closed_for_gc and retransmit_count == 0 and !send.hasUnackedData()

`hasUnackedData()` has to treat the FIN separately from the bytes. ACK ranges
cover byte offsets and the FIN is not a byte, so `ack_offset` stops at
`write_offset` and can never show the FIN as delivered — the original
`ack_offset < write_offset + 1` test was true forever, which made every stream
that had ever sent a FIN permanently unacknowledged. `SendStream.fin_acked` is
set from the `fin` flag of the acked frame instead. RESET_STREAM ends the send
side the same way: RFC 9000 §3.1 forbids STREAM frames after it, so its unacked
bytes are never coming back.

Three places evaluate it, all through `StreamsMap.disposeIfSettled()`:

1. **ACK processing** — the ACK that retires the last unacked byte is the exact
   moment the stream stops being needed. O(1), and the path that fires for
   almost every stream.
2. **STREAM+FIN handling** — for a stream whose send side was already settled
   when the peer's FIN arrived.
3. **`collectClosedStreams()`** — a sweep that catches whatever the other two
   missed: the 64-entry disposal queue is allowed to fill, and a stream can
   settle without any further ACK arriving to trigger a check. `needs_gc_scan`
   stays set while any stream is still awaiting reclamation.

Disposal is deferred rather than immediate. `disposeIfSettled` only queues the
stream ID; `StreamsMap.drainDisposalQueue()` removes and frees it, and the
event loop calls that once per cycle, *after* the protocol layer has polled.
An H3 or WebTransport `poll()` loop therefore always sees a live stream for the
data that arrived in the same cycle.

## Receive-only streams

A unidirectional receive stream has no send side to wait for an ACK on, so
`ReceiveStream.isDisposable()` is a different predicate: the data is all out
(`finished`, or `sorter.isComplete()`, or the peer reset it) **and** the
consumer has said it will not read again.

That second half is the part that cannot be inferred. `finished` flips inside
`read()`, which is called by the protocol layer itself, so at that instant the
layer has the bytes but has not yet delivered them — and it still holds
per-stream state keyed by the ID: H3's control and QPACK streams, WebTransport's
`stream_bufs` and `fin_delivered`. Reclaiming on `finished` alone would drop a
WebTransport FIN event on the floor and would let a peer close a critical stream
without `checkCriticalStreams` ever seeing it.

So the consumer calls `StreamsMap.releaseRecvStream(id)` at the point it has
handed the FIN to the application — the two FIN-delivery sites in
`WebTransportConnection.pollWtStreamData`, and the plain-QUIC uni loops in
`event_loop.zig`. H3's critical streams are never released and so are never
reclaimed, which is the right answer by construction rather than by special
case. Both `identifyPeerUniStreams` and `identifyWtUniStreams` also release a
stream that finished without ever becoming identifiable, so a peer cannot leak
one `ReceiveStream` per zero-length uni stream it opens.

Release is O(1) and queues onto the same disposal queue bidi streams use.
Because nothing re-offers a released stream, a dropped enqueue would strand it;
`recv_disposal_overflow` makes the next drain re-scan `recv_streams` instead.

## Frames for a stream that is gone

Under loss the peer retransmits data we acknowledged just before reclaiming the
stream. `getOrCreateStream()` would build a fresh `Stream` for it — one nothing
would ever close, whose close would be counted a second time against
MAX_STREAMS. `StreamsMap.next_peer_bidi_to_open` is the watermark that separates
the two cases: an ID below it was opened and reclaimed, and
`error.StreamAlreadyClosed` tells `connection.zig` to drop the frame.
`next_peer_uni_to_open` does the same for `getOrCreateRecvStream`, and a
retransmitted FIN is kept from counting twice by `ReceiveStream.closed_counted`.

The watermark is exact only because §3.2's implicit opening is honoured. A peer
may use stream IDs out of order, and using ID *n* opens every lower ID of the
same type; `getOrCreateStream` materialises those lower streams before returning
the requested one. Without that, an ID below the watermark could still be a
stream we had never been told about, and rejecting it would drop a legitimate
new stream.

The number of streams a peer can make us materialise is bounded by the
MAX_STREAMS credit we granted: `connection.zig` raises STREAM_LIMIT_ERROR for an
ID at or above `max_incoming_bidi_streams` before `getOrCreateStream` is
reached.

## The allocator matters

Reclaiming a stream returns its buffers to whatever allocator the application
gave the connection. Every server in `apps/` used to pass an `ArenaAllocator`,
where `free` is a no-op — the stream was gone from the map but its memory was
not reusable, and the process still grew linearly. They pass
`std.heap.smp_allocator` now. Clients keep the arena, because they exit.

## Send buffers

`SendStream.write_buffer` is indexed relative to `buf_base`, the stream offset
of its first byte, not by absolute offset — `bufferedAt()` is the only way in.
`onAck` drops the acknowledged prefix, so a stream holds roughly what is in
flight rather than everything it has ever sent.

Two conditions gate the memmove, and both matter. A flat 64 KiB threshold on
its own is quadratic against an application that writes ahead: an 8 MB write
acknowledged in 64 KiB steps copies ~512 MB and costs two thirds of bulk
throughput (20.0 → 7.2 MB/s on `tools/bench_local.sh`). Requiring the discarded
prefix to be at least as large as the remainder makes the copying amortised
O(1) per byte, and the benchmark is back to unchanged.

`ack_offset` is the safe watermark because it is where PTO retransmission
starts (`queueStreamPtoRetransmissions`). Loss detection can still name a range
below it — a lost packet whose bytes a later ACK covered — so `queueRetransmit`
trims to `ack_offset` rather than reaching for bytes that are gone.
