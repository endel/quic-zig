### Every remaining failure is one test case

`rendezvous-timeout` wants `REQUEST_ERROR` with code `TIMEOUT` (0x2). Five of
the eight relays answer `DOES_NOT_EXIST` (0x10) or `404` instead — imquic,
moqx, stitcher-moq, moqtail and `cdn.moq.dev`. Three answer `TIMEOUT` and
pass: moq-rs-draft-18, moqt-nr, moxygen.

The runner's
[TEST-CASES.md](https://github.com/englishm/moq-interop-runner/blob/main/docs/tests/TEST-CASES.md)
is unambiguous — "REQUEST_ERROR received with error code TIMEOUT" — so our
client is reading the spec correctly and the majority of the ecosystem is
not. Answering "the track does not exist" to a SUBSCRIBE for a namespace
nobody publishes is a defensible reading, which is probably why it is common.

**This is not ours to decide quietly.** Loosening our check to accept
`DOES_NOT_EXIST` would take us to 14/15 while hiding a real conformance
disagreement. Raising it with the runner's maintainers is the honest route;
there is no issue open about it as of 2026-09-11.

Re-run after the relay work below, which also made the client stricter about
parameters the draft says are session-fatal: the same 6/15, and not one
pairing failed on a decode. The rows that moved are the two remote relays
being remote — imquic missed `announce-subscribe` on both transports this
time (the footnote above), and moqtail answered neither the SETUP in
`announce-only` nor the PUBLISH_NAMESPACE in `announce-subscribe`.

| moqlivemock (`mlmtest`) | 0/6 | raw QUIC only; our relay image is WebTransport |

Four bugs, none of which our own client could see — it agrees with whatever we
emit, which is the same trap the draft-17 control messages fell into. Three
were ours and are fixed; the fourth is the peer's.

### 1. Stale content across broadcasts (fixed)

`publish-track-subscribe` received `publish-track-only`'s payload. A track's
cached groups outlived the publisher that produced them, so the next
subscriber was replayed a finished broadcast. Clearing the cache when the
publisher's session closes is not enough — the relay hands the track to a new
publisher while the old one is still connected — so it is dropped on takeover
too.

### 2. A subscription that never ended (fixed)

With the cache fixed, the same test timed out instead, and the earlier reading
of it — "the subscriber never gets a payload" — was wrong. Its trace shows the
object arriving and being decoded (`recv_subgroup: completed object #1`). What
never arrived was the end of the subscription: the test joins three futures,
and the one waiting for the subscription to finish never returned.

Our relay ignored the publisher's PUBLISH_DONE — the log line was
`client 2 request type=0xb` — so the subscriber waited the full ten seconds
for objects that were never coming. §10.11 makes that the relay's job to say:
each downstream subscription is its own, and each needs its own PUBLISH_DONE
carrying the number of data streams *this relay* opened for it, not the count
the upstream sent. A publisher that disconnects without one gets the same
message sent on its behalf, with `TRACK_ENDED`.

The same comparison turned up what else we put on a forwarded stream: §2.2
says a relay forwarding a subgroup that begins with the subgroup's first
object MUST set the SUBGROUP_HEADER's FIRST_OBJECT bit, and our header writer
had no way to express it, so every forwarded stream claimed the opposite.
(`in_hdr=55…` from the publisher, `out_hdr=11…` from us.) It is a draft-18
bit; draft-17 has no such thing and the writer takes the draft.

### 3. Namespace discovery was missing from the WebTransport relay (fixed)

moq-dev-rs's `announce-subscribe` timed out "waiting for the test namespace
announcement". Its subscriber discovers namespaces before subscribing, and our
WebTransport relay dropped SUBSCRIBE_NAMESPACE on the floor —
`client 1 request type=0x50`. §6.2 makes answering it a MUST for a relay that
holds the namespace. It now replies REQUEST_OK, pushes a NAMESPACE for each
namespace already under the prefix, and pushes later arrivals as they are
announced; when the last announcer of a namespace leaves, its subscribers get
NAMESPACE_DONE.

The raw-QUIC relay had answered SUBSCRIBE_NAMESPACE all along, but wrongly in
two ways nobody had exercised: it hand-parsed the message with draft-17's
field list, so a draft-18 sender was read one varint out of step, and it sent
the whole namespace where §10.16 asks for the part after the prefix.

### 4. moxygen's SUBSCRIBE is not decodable, and that is theirs (open, upstream)

`REQUEST_ERROR → client: code=18 malformed subscribe` on every SUBSCRIBE from
Meta's client. The capture names the field:

```
payload(33B)=00 01 0b "nonexistent" 0d "no-such-track" 01 21 02 80fa
             └id └tuple            └name             └1 param
                                                       └─ 0x21 SUBSCRIPTION_FILTER, len 2, filter type 250
```

Filter type **250** is moxygen's private `LocationType::LargestGroup`, which
their own source marks as non-spec. draft-18 §5.1.2 defines 0x1–0x4 and says
an endpoint receiving anything else MUST close the session with
PROTOCOL_VIOLATION. Their *relay* accepts our SUBSCRIBE — we reach it 7/7 —
because their parser whitelists 250 on the way in.

It is already reported as
[moxygen#225](https://github.com/facebookexperimental/moxygen/issues/225)
(filed 2026-09-02 by kixelated, still open), which records the reference
relay refusing it the same way: `moq_net::ietf::session: session error
err=invalid value`.

So we kept refusing it, and made the refusal the one the draft asks for: a
session close with PROTOCOL_VIOLATION rather than a REQUEST_ERROR. Same score
either way, because their client counts a session close as a request error —
which is the other half of that issue: `subscribe-error` and
`subscribe-before-announce` "pass" against us for the wrong reason, on a
SUBSCRIBE we never parsed. moxygen is honestly 3/6, not 5/6.

### The two 0/n rows are a transport gap, not a protocol one

imquic's and moqlivemock's test clients dial **raw QUIC** whatever the URL's
scheme says — imquic offers ALPN `moqt-19, moqt-18, moqt-17, moqt-16` and
mlmtest offers `moqt-18` against `https://relay:4443`, and our WebTransport
relay answers `h3` alone, so the handshake ends in `no_application_protocol`.
Our raw-QUIC relay would have answered them; it is a different binary, and the
image ships the WebTransport one because the harness's compose file dials
`https://`. A relay that served both ALPNs on one port would collect both
clients — moqlivemock's own entry says it does exactly that. That is the next
piece of work, not a bug in what is there.
