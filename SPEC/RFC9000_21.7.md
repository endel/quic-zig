# RFC 9000 §21.7 — Stream Fragmentation and Reassembly

What a receiver owes a sender that withholds bytes on purpose, and what bounds
the reassembly buffer. Covers §21.7 together with the buffering duty of §2.2
and the CRYPTO ceiling of §7.5, because one structure serves all three.

Implementation: `src/quic/stream.zig` (`FrameSorter`),
`src/quic/crypto_stream.zig` (`CryptoStream`), `src/quic/limits.zig` (the two
caps), `src/quic/connection.zig` (error mapping).

## What the spec asks for

Buffering out-of-order data is mandatory, so this cannot be solved by dropping
it (§2.2):

> Endpoints MUST be able to deliver stream data to an application as an ordered
> byte stream. Delivering an ordered byte stream requires that an endpoint
> buffer any data that is received out of order, up to the advertised flow
> control limit.

Only *duplicate* data at an already-received offset may be discarded. §2.2 also
warns that frame boundaries are not preserved across retransmission, so
overlapping arrivals are ordinary traffic rather than an edge case.

§21.7 then describes the attack this document exists for:

> An adversarial sender might intentionally not send portions of the stream
> data, causing the receiver to commit resources for the unsent data. This
> could cause a disproportionate receive buffer memory commitment and/or the
> creation of a large and inefficient data structure at the receiver.

> QUIC deployments SHOULD provide mitigations for stream fragmentation attacks.
> Mitigations could consist of avoiding overcommitting memory, limiting the
> size of tracking data structures, delaying reassembly of STREAM frames,
> implementing heuristics based on the age and duration of reassembly holes, or
> some combination of these.

No structure is mandated. "Limiting the size of tracking data structures" is
the mitigation we take.

CRYPTO is the sharper case (§7.5): those frames are not flow controlled, so
nothing bounds them but our own ceiling, and the peer is unauthenticated the
whole time. The floor is 4096 bytes, and exceeding the buffer is a MUST-close:

> Implementations MUST support buffering at least 4096 bytes of data received
> in out-of-order CRYPTO frames.

> If an endpoint does not expand its buffer, it MUST close the connection with
> a CRYPTO_BUFFER_EXCEEDED error code.

## What we do

`FrameSorter.chunks` is a `std.ArrayList(Chunk)` of `{offset, data}` held
sorted ascending and never overlapping. Sorted order is the whole point: it
makes overlap resolution a binary-search probe of the neighbouring run.

| Operation | Cost | Note |
|---|---|---|
| `push` appending at/after the high-water mark | O(1) | the bulk-receive fast path |
| `push` below the high-water mark | O(log n) probe + O(k) overlapping runs | `lowerBound`, then a walk |
| `pop` | O(1) | only `items[0]` can hold `read_pos` |
| insert / remove | O(n) memmove | 24-byte elements, capped at 1000 |

Two ceilings, both in `limits.zig`:

- `max_reassembly_chunks` = 1000 distinct runs per sorter. Past it `push`
  returns `error.TooManyChunks`, which `connection.zig` turns into
  INTERNAL_ERROR. Applies to stream *and* crypto sorters.
- `max_crypto_stream_offset` = 16 KiB (tracks `tls_handshake_in`, the most of
  one peer flight the TLS layer can stage), measured past what TLS has
  consumed at that encryption level. Beyond it `CryptoStream` returns
  `error.CryptoBufferExceeded` → CRYPTO_BUFFER_EXCEEDED. Comfortably above the
  4096-byte floor §7.5 requires, and relative so that a long-lived 1-RTT
  CRYPTO stream (session tickets) never accumulates into it.

In-order data does not spend the chunk budget: a frame that starts where the
newest chunk ends grows that chunk (doubling its allocation, up to 64 KiB)
instead of adding one. So a stream whose consumer has paused — a proxy
holding back a request body — keeps a window's worth of unread data in a few
dozen chunks, not one per frame. Before this, 1000 unread in-order frames
(~1.3 MB, below the default 6 MB stream window) closed the connection with
INTERNAL_ERROR. A chunk that was grown is copied once on `pop`, because the
caller frees exactly the slice it receives.

The two work together: the cap bounds the worst case, the sorted array lowers
the cost of reaching it. Neither alone is sufficient — a cap over the old hash
map still allowed a 1000-deep quadratic scan per push, and a sorted array with
no cap still lets a peer pin unbounded runs.

## Why a sorted array

Survey of what other stacks do, since the RFC declines to say:

| | Fragment index | Gap tracking | Bytes | Cap |
|---|---|---|---|---|
| quic-go | `map[offset]` | linked list, O(g) | zero-copy frame slice, `DoneCb` | 1000 gaps |
| ngtcp2 | `dataksl` B+tree | `gapksl` B+tree | copy into 8 KiB shared chunks, lazily allocated | 4000 gaps |
| quiche | `BTreeMap` keyed by *end* offset | implicit | `Arc<[u8]>` | flow control only |
| quinn | sorted `VecDeque` | implicit | `Bytes` + `defragment()` | 1024 chunks |
| msquic | flat circular arena | `QUIC_RANGE` intervals, 8 inline | memcpy to final position | window |
| mvfst | deque of IOBuf chains | implicit between elements | zero-copy IOBuf | none |
| lsquic | both, switched at runtime | list / per-byte bitmask | nocopy or 4 KiB copy | >5 holes, <64 B avg |

Two families: an arena plus an interval set (msquic, lsquic's hash mode), where
metadata scales with *holes* and duplicate suppression is free; or an ordered
sequence of received buffers, where metadata scales with *fragments* but the
in-order path copies nothing. Everyone except quiche and mvfst caps the count.

We are in the second family, and two local constraints keep us there:

- `read()` transfers ownership of a heap slice, and roughly eighteen call sites
  across `event_loop.zig`, `h3/`, and `webtransport/` free what they get. An
  arena hands back borrowed slices into a buffer it still owns, so adopting one
  means rewriting all of them.
- An arena would *raise* baseline memory for our workload. An in-order stream
  currently holds one chunk — pushed, popped, freed — whereas a per-stream ring
  holds its block for the stream's lifetime. With the many short streams that
  MoQ and WebTransport open, that is the wrong direction, and the opposite of
  what a461a81 did for per-connection memory. ngtcp2 allocates its reorder
  buffer lazily for the same reason; we get that property for free.

The zero-copy trick the other stacks lean on (`Arc<[u8]>`, `Bytes`, quic-go's
`DoneCb` refcount) has no Zig equivalent here. Retaining datagram buffers
instead of duplicating would be a real gain, but it is a refcounting project
orthogonal to the complexity bug, and it is what makes our per-chunk `dupe` of
a one-byte frame the worst of both worlds today.

## Measurements

A/B of the old hash map against the sorted array, ReleaseFast, same machine,
pushing disjoint out-of-order runs below the high-water mark:

| chunks | hash map | sorted array | |
|---|---|---|---|
| 1 000 | 0.286 ms | 0.028 ms | 10× |
| 8 000 | 15.098 ms | 0.310 ms | 49× |
| 32 000 | 235.736 ms | 1.446 ms | 163× |

The speedup growing with n is the complexity class changing, not a constant
factor. In-order bulk receive (100 k × 1200 B) is unchanged at 3.13 → 2.96 ms:
the append fast path never scanned anything and still doesn't.

Shipped code under the cap, which is what an attacker can actually reach:
62 ns/push filling the ceiling ascending, 236 ns/push descending (the sorted
array's own worst case — every insert shifts the array), and 0.188 ms for a
single frame covering all 1000 buffered runs. The 32 000-chunk row above is now
unreachable by construction.

Correctness: 400 randomized overlap/gap trials against an oracle that fixes
byte *o* to `o % 251`, so any reordering must reproduce it; plus the repo suite
(753 tests) and the fuzz suite (608, including target 18, which drives this
type adversarially).

## Caveats

- **Only appends coalesce.** A frame extending the newest chunk merges into
  it; one filling a hole between two runs does not join them. A thousand
  one-byte holes stay a thousand entries; the cap is what bounds them.
  quinn's `defragment()` and ngtcp2's 8 KiB chunks both do better on memory
  per hole.
- **The cap is per sorter**, so per receive stream and per encryption level —
  not a connection-wide budget. A peer opening many streams multiplies it, and
  that is bounded only by MAX_STREAMS.
- **Hitting the cap kills the connection** rather than dropping the frame.
  §21.7 also permits delaying reassembly, which we do not do; this matches
  quic-go, quinn, and ngtcp2, and at 1000 runs a legitimate path will not reach
  it.
- **The byte bound is the stream window.** Per-stream receive flow control is
  enforced (FLOW_CONTROL_ERROR past `receive_window`), so one stream holds at
  most its window. The connection-level bound is weaker — see
  [RFC9000_3.md](RFC9000_3.md).
- The descending-insert worst case is O(n) memmove per push. Cheap at this cap
  (24 KB of contiguous move), but it is the reason to revisit the structure
  before raising `max_reassembly_chunks` much beyond 1000.
